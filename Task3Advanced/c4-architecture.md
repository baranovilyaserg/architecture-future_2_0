Целевая архитектура Future 2.0 на 3 года

Текущее состояние (0 месяцев)

Проблемы текущей архитектуры:
- Монолитный DWH с встроенной бизнес-логикой
- Синхронные интеграции через ESB Camel (узкое место)
- Batch отчётность занимает часы
- Невозможность масштабирования отдельных доменов
- Медицинские и финансовые данные в одном хранилище
- Сложность добавления новых бизнес-направлений

Целевое состояние (36 месяцев) - Event-Driven Data Mesh

Фаза 1: Пилот (0-6 месяцев)

Компоненты:
- Финтех домен: выделен в отдельный microservice
- Kafka/RabbitMQ: база для event streaming
- Schema Registry: каталог схем событий (Avro/Protobuf)
- Внутренние сервисы: начало миграции на события
- DLQ очереди: обработка сбойных событий
- Витрина данных v1: простая витрина на основе подмножества данных

Остаются в Legacy:
- DWH (SQL Server 2008)
- PowerBuilder UI
- ESB Camel (как мост совместимости)
- Power BI (постепенно заменяется)

Фаза 2: Расширение (6-18 месяцев)

Новые компоненты:
- Клиники домен: Event Sourcing для пациентских данных (без медкарт)
- ИИ операции домен: собственные события
- Stream analytics (Kafka Streams / Flink): обработка потоков
- Антикоррупционные слои: для интеграции с DWH/Camel
- Витрина данных v2: расширенная, поддерживает больше срезов данных
- API Gateway: для синхронного доступа

Миграция:
- Вывод новых доменов из ESB Camel
- Данные пациентов (неконфиденциальные) - миграция в витрину
- Power BI постепенно интегрируется с витриной

Фаза 3: Отказ от легаси (18-36 месяцев)

Удаляются/выводятся:
- ESB Camel (полностью)
- Direct интеграции DWH (заменены событиями)
- PowerBuilder UI (заменён новым интерфейсом на базе API)

Остаются как Legacy Bridge:
- DWH (только для исторических данных, read-only)

Полностью Event-Driven:
- Все домены взаимодействуют через события
- Витрина данных - основной источник для BI
- Реал-тайм аналитика через Stream Processing
- Масштабирование каждого домена независимо

Компоненты целевой архитектуры (C4 - уровень компонентов)

User Interfaces:
- Витрина данных веб-интерфейс (React/Vue)
- Mobile App (для клиник)
- Admin Dashboard

API Layer:
- API Gateway (Kong/AWS API Gateway)
- REST/GraphQL endpoints
- Event Publishing API

Event Infrastructure:
- Message Broker (Kafka / RabbitMQ / AWS SQS)
- Schema Registry (Confluent / AWS)
- Dead Letter Queue handlers

Domain Services:
- Финтех Service (Go/Java) - кредиты, платежи
- Клиники Service (Python/Go) - пациентский поток (не медкарты)
- ИИ Service (Python) - диагностика
- Аналитика Service (Python/Scala) - расчеты KPI
- Витрина Service (SQL/Python) - хранилище витрины

Data Storage:
- Event Log (Event Store)
- Витрина данных (PostgreSQL/Snowflake)
- Cache (Redis)
- DWH Legacy (SQL Server, read-only)

Observability:
- Prometheus + Grafana
- ELK Stack (логи)
- Jaeger (трейсинг)

Миграция данных

1. Пациентские данные (неконфиденциальные):
   - Выбрать срезы без медкарт и диагнозов
   - Снять снимок из DWH
   - Загрузить в витрину
   - Настроить CDC (Change Data Capture) для синхронизации

2. Финансовые данные:
   - Миграция полностью в Финтех домен
   - Аудит trail для регулятивов
   - Шифрование в transit и at rest

3. Операционные данные:
   - Распределить по доменам
   - Настроить события для синхронизации

Безопасность и регулятивы

Медицинские данные (исключены из витрины):
- Медицинские карты: остаются в DWH (read-only для аналитиков)
- Диагнозы: не публикуются в события
- Результаты исследований: не попадают в витрину

Финансовые данные (кредиты, счета, платежи):
- Все события подписаны (signable contracts)
- Audit trail для всех операций
- Шифрование PII (ФИО, документы) в витрине
- Соответствие требованиям банковской лицензии

Доступ:
- RBAC для витрины данных
- Row-level security для конфиденциальных срезов
- API авторизация через OAuth2/JWT
