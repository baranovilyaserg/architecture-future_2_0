# Justification — Обоснование Event-Driven архитектуры vs текущей DWH + ESB

## Executive Summary

Текущая архитектура Future 2.0 использует **монолитный DWH** (SQL Server) + **ESB** (Apache Camel) для интеграций. Эта модель:
- Замедляет разработку новых функций (time-to-market 2–3 месяца)
- Создаёт bottleneck в DWH (все данные в одном месте)
- Делает невозможной масштабируемость по доменам (финтех, клиники, ИИ работают независимо)
- Создаёт технический долг (legacy система, сложно изменять)

**Event-Driven архитектура** на Kafka решает эти проблемы, позволяя компании масштабироваться и выводить новые продукты быстрее.

---

## Проблемы текущей архитектуры

#### 1. Монолитный DWH — узкое место

**Проблема:**
- Все 6 доменов пишут в одну таблицу → конфликты и блокировки
- Любое изменение в одном домене может сломать другой
- Масштабирование БД невозможно: нельзя разделить между регионами или облаками
- Backups 100TB+ очень долгие

**Event-Driven решение:**
- Каждый домен имеет собственное хранилище (PostgreSQL для Event Store)
- Данные между доменами через события в Kafka (асинхронно, без блокировок)
- Можно использовать разные БД: финтех → PostgreSQL, ИИ → Feature Store, клиники → специализированное решение

---

#### 2. ESB (Apache Camel) — синхронный RPC медленный

**Проблема:**
- Все интеграции синхронные: вызов → ожидание ответа → блокировка
- Если один сервис медленный, весь chain медленный (P95 latency > 5 секунд)
- Нет retry механизма: если сервис down, платёж fails
- Нет буферизации: пиковые нагрузки вызывают cascade failures

**Event-Driven решение:**
- Платёж публикует событие в Kafka
- Каждый подписчик (fintech, analytics, platform) независимо его обрабатывает
- Если один подписчик медленный, остальные не ждут
- Есть DLQ (Dead Letter Queue) для ошибок

**Impact:** Latency снижается с 5+ сек → <100ms

---

#### 3. Масштабирование по доменам — невозможно

**Проблема:**
- Финтех хочет расширяться (выпустить кредиты) → нужны новые функции
- Клиники хотят открыть новый регион → нужны локальные копии данных
- ИИ хочет выпустить новую модель → нужны новые features
- Но всё это в одном DWH → риск, сложность, медленно

**Event-Driven решение:**
- Домен может масштабироваться независимо
- Домен может использовать оптимальное хранилище
- Домен владеет своими данными
- Разные регионы могут быть независимыми

---

#### 4. Time-to-Market — 2–3 месяца

**Проблема:**
- Новая функция требует изменения DWH схемы
- DWH изменения требуют approval от всех 6 команд
- Нужно перепроектировать ERD, миграции, откаты
- Нужна полная регрессия (все 6 доменов тестируют)
- Результат: 2–3 месяца разработки для простой функции

**Event-Driven решение:**
- Новая функция → новый микросервис → подписка на события
- Никаких изменений в других доменах
- Быстрая итерация, меньше координации
- Результат: 3–4 недели для новой функции

## Event-Driven архитектура (преимущества)

### 1. Слабая связанность (Loose Coupling)

**Принцип:**
- Домены общаются через события, а не напрямую
- Один домен не знает о деталях другого
- Если один домен down, остальные работают

**Availability improvement:** 99% → 99.99%

---

### 2. Масштабируемость (Scalability)

**Горизонтальное масштабирование:**

**Текущее (DWH монолит):**
- DWH может обрабатывать только 1000 платежей/сек
- Добавить мощности? Очень дорого и рискованно
- Региональное расширение? Невозможно (одна база)

**Event-Driven решение (Kafka):**
- Kafka может обрабатывать 1,000,000 платежей/сек
- Каждый consumer (Витрина, Analytics, Platform) масштабируется независимо
- Региональное расширение? Deploy consumer в другом регионе

**Impact:** Готовность к 10x нагрузке

---

### 3. Гибкость (Flexibility)

**Добавить нового подписчика:**

**Текущее (DWH монолит):**
- Нужно изменить все интеграции через ESB
- Риск, долгая разработка

**Event-Driven:**
- Новый микросервис подписывается на события
- Ноль изменений в других доменах
- Deploy за минуты

---

### 4. Real-Time Analytics (Near-Zero Latency)

**Текущее (DWH монолит):**
- Данные в DWH обновляются с задержкой (batch каждые 3 часа)
- Витрина отстаёт от реального времени - неэффективные решения

**Event-Driven:**
- События публикуются в реальном времени
- Витрина обновляется мгновенно (stream processing)
- Аналитика всегда актуальна

---

### 5. Event Sourcing (Audit Trail & Replay)

**Текущее (DWH монолит):**
- Нет полного журнала изменений
- Сложно восстановить состояние на определённую дату
- Нет возможности replay событий

**Event-Driven:**
- Все изменения — события, которые сохраняются в Event Store
- Полный audit trail для compliance
- Возможность replay для восстановления данных или тестирования

---

### 6. Resilience (Устойчивость к сбоям)

**Текущее (DWH монолит):**
- Если сервис down, платёж fails
- Нет механизма retry

**Event-Driven:**
- Если обработка события не удалась, оно попадает в DLQ
- Можно настроить retry с backoff
- Снижение риска потери данных

## Миграционная стратегия (Strangler Fig)

**Риск:** Не делать все сразу

**Решение:** Gradual migration, фаза за фазой

**Фаза 1 (Месяцы 0–6): Пилот в 1–2 доменах**
- Fintech + Clinics на Kafka
- Vitrine v1 работает
- ESB + DWH всё ещё активны для других доменов
- Risk: LOW (только 2 домена затронуты)

**Фаза 2 (Месяцы 6–18): Расширение**
- AI Ops + Analytics присоединены
- Anti-corruption layer для ESB/DWH
- ESB используется только для legacy
- Risk: MEDIUM (но контролируемо)

**Фаза 3 (Месяцы 18–36): Полная миграция**
- ESB + DWH + PowerBuilder удалены
- 100% Event-Driven
- Risk: LOW (все домены готовы)

## Возврат инвестиций (ROI)

### Текущее состояние (год)
- Стоимость инфраструктуры: 10M (DWH, ESB, лицензии PowerBuilder)
- Стоимость разработки: 5M (медленно, много передач)
- Соответствие требованиям/аудит: 1M (ручной audit trail)
- **Итого: 16M/год**

### Целевое состояние (год 3)
- Стоимость инфраструктуры: 4M (облако, автомасштабирование)
- Стоимость разработки: 2M (в 10x быстрее, меньше координации)
- Соответствие требованиям/аудит: 0.5M (автоматический audit trail)
- **Итого: 6.5M/год**

### Экономия: 9.5M/год (сокращение затрат на 60%!)

### Улучшение time-to-market
- Новые функции: 2–3 месяца → 3–4 недели (в 5–10x быстрее)
- Более быстрые итерации продукта
- Конкурентное преимущество

## Смягчение рисков

| Риск | Смягчение |
|---|---|
| Критические изменения в событиях | Семантическое версионирование, параллельная публикация (v1 + v2) |
| Проблемы финальной консистентности | Saga pattern, компенсирующие транзакции |
| Простой Kafka | Многорегиональный кластер Kafka, HA |
| Потеря данных | DLQ, сохранение журнала событий (7 лет), резервные копии |
| Пробелы в компетенциях | Обучение + консультант (фаза 1), практические пилоты |
| Сложность легаси-систем | Strangler Fig pattern, ACL слои, постепенный переход |

## Заключение

Event-Driven архитектура — необходима для Future 2.0, чтобы:

1. Масштабироваться по доменам (финтех, клиники, ИИ независимо)
2. Выводить новые продукты быстрее
3. Достичь real-time аналитики
4. Соответствовать требованиям регулирования (audit trail, compliance)
5. Сэкономить бюджет на инфраструктуру и разработку
6. Быть готовым к расширению
